# Preparing an authorized real-data case

The classroom generator needs no account or external flight data. This guide covers
the next step: a small local experiment using recordings and trajectories you are
authorized to analyze. It does not claim that the example's accuracy transfers to
field recordings.

If the location is initially only a country or continent, start with the
[investigation workflow](INVESTIGATION_WORKFLOW.md). For daily archive acquisition,
download times and disk requirements, see [download and storage](DATA_VOLUME.md).
This page covers preparing the smaller case after candidate selection.
The [broad-search guide](BROAD_SEARCH.md) documents acquisition,
regional screening and `export-candidate`; [native builds](BINARIES.md) can run that CLI
without a separate Python installation.

## Keep a provenance record

Preserve the original media, its SHA-256, source/permission, acquisition time, original
sample rate and channels. Record the evidence for the first sample's UTC time and its
uncertainty. If extracting a clip, record the clip offset, tool command and output hash.
Playback edits and codec priming can affect alignment. Treat timestamps from editing
software, upload pages and filesystem metadata as claims requiring corroboration.

Store flight-data provider, retrieval date, dataset version, covered period, bounding
area, license, source field definitions and raw-file hashes. Keep the chosen trajectory
sampling and any filters. Do not distribute raw provider data merely because an API
allowed you to read it.

## Audio extraction and inspection

For a long original video, begin with [`review-media`](REAL_RECORDING.md). It creates
overlapping review chunks and keeps their original-media offsets. For a known local
time window, the same guide explains `download-window` and its ready-to-import
`tracks/geographic.csv`. Daily archives remain available for broader searches.

From the native executable's folder, in Windows PowerShell. On macOS/Linux use
`./doppler-lab` and forward slashes; source installs can use their environment's
`doppler-lab` command. Replace the example recording path with your original file:

```powershell
.\doppler-lab.exe extract "C:\recordings\owned-recording.webm" --start 120 --duration 180 --output work\field\recording.wav
.\doppler-lab.exe inspect work\field\recording.wav --channel 0 --window 2 --hop 0.25 --max-hz 600 --output work\field\inspection.png
```

FFmpeg is optional for PCM WAV input. Extraction preserves the input's channel layout;
analysis defaults to channel zero. Compare channels when the recording is stereo.
The output rate is 8 kHz, intended for the low-frequency study band. Retain full-rate
originals for other acoustic analysis. Use new output names; the commands will not
overwrite evidence.

Select contiguous windows with a plausible curved tone and sufficient signal on both
sides of closest approach. Check harmonics and nearby contamination. In this release,
event selection and aircraft candidate preparation are analyst tasks. A moving line
could be a vehicle, instrument, playback effect or other source; it is not automatically
an aircraft. Do not fit the edited narration track as if it were the original field recording.

Optionally trace a ridge in your spectrogram tool and export:

```csv
time_s,frequency_hz
15.0,165.2
20.0,161.8
```

Provide at least 12 actual points spanning >=10 seconds, then run:

```powershell
.\doppler-lab.exe fit-ridge work\field\ridge.csv
```

The two rows above describe the schema, not a valid complete fit. Use the estimates as
broad screening bounds and inspect residuals; do not report them as exact flight parameters.

## Normalize tracks deliberately

The solver's CSV format is:

```csv
track_id,time_s,east_m,north_m,up_m
flight-A-segment-1,0,1000,1500,1200
flight-A-segment-1,2,1150,1515,1201
```

At least four strictly increasing samples are needed for each track ID. Split at
large gaps and keep each segment's ID unique. The default case gap limit is 5 s; the
demonstration uses 3 s. Do not interpolate long missing intervals to manufacture support.
Airframe IDs can span multiple flights; segment them before event association. Distinct
segment IDs also do not establish independent aircraft identity: the analyst must check.

For geographic input, first prepare a provider-independent CSV:

```csv
track_id,timestamp_utc,latitude_deg,longitude_deg,height_ellipsoid_m
example,2026-11-03T20:00:00Z,33.1,-112.1,1600
example,2026-11-03T20:00:02Z,33.101,-112.1,1601
```

Those are fictional schema examples. Convert a complete file using a declared origin:

```powershell
.\doppler-lab.exe import-tracks work\field\geographic.csv --origin 33.1 -112.1 400 --time-origin 2026-11-03T20:00:00Z --output work\field\tracks.csv
```

The importer requires WGS84 ellipsoid heights and timezone-aware timestamps. It converts
through ECEF to local ENU. Units matter: feet ×0.3048 gives metres; knots ×0.514444 gives
metres/second, but the solver derives velocity from positions rather than trusting a
reported speed column. Ground-relative track motion is used only under the still-air
assumption. Wind is not corrected by casually subtracting one constant speed.

**Do not relabel pressure altitude as `height_ellipsoid_m`.** GNSS height, orthometric
terrain height and pressure altitude are different quantities. If using an orthometric
height `H`, the compatible ellipsoid height is `h = H + N`, where `N` is the appropriate
geoid separation for the chosen horizontal/vertical references. Use a documented
transformation for actual data. Missing or incompatible height means the case is not
ready for geometric matching. See [NOAA vertical datums](https://geodesy.noaa.gov/datums/vertical/index.shtml).

## Receiver points and terrain

Version 0.3.0 adds `download-terrain`, `terrain-point` and `prepare-observers` for
USGS 3DEP in the contiguous US. The [terrain guide](TERRAIN.md) provides native commands,
offline reuse, recorded datum-conversion grids and height-sensitivity instructions.
Broad screening accepts `--terrain` instead of a constant `--receiver-height`.

A small flat demonstration can use `grid.up_m`. A real sloping site should supply an
`observers.csv` with `east_m,north_m,up_m` for every candidate, converted into the **same**
ENU frame as the aircraft. Include microphone height above ground before conversion.
Set `"observers": "observers.csv"` in the case instead of `"grid"`.

An ENU `up` coordinate is not simply a global height minus the origin height over a
large area; the ECEF-to-ENU transformation accounts for the curved reference geometry.
`prepare-observers` writes terrain-following ENU candidates, their geographic coordinates
and the exact origin. Use that same origin for aircraft-track import. Other terrain
providers and arbitrary coordinate-reference conversions remain analyst preparation.
Detailed matching retains ENU values; `geographic.csv` preserves the candidate mapping.

## Manifest

Copy the generated `case.json` as the schema example and replace the fictional inputs.
Required fields are `schema_version: 1`, `coordinate_system: "local_enu_m"`, `audio`,
`tracks`, `provenance`, `time_basis`, `clock_offset_s`, `events`, and either `grid` or
`observers`. Include `origin_wgs84` and `track_epoch_utc` as provenance metadata if
using geographic inputs; the solver does not infer conversions from these metadata.

Every range is `[minimum, maximum, step]`; values at or below the maximum are sampled.
An exact known clock uses `[offset, offset, 1]`. For example, if the track epoch is
20:00:00Z and the first retained audio sample is 20:03:00Z, `clock_offset_s` is around
180, not zero. Each event has `name`, `start_s`, `end_s`, `source_hz` and `track_ids`.
Use nonoverlapping windows for separate flyovers. One stable harmonic can be the selected
tone, but multiple harmonics are one event.

All input paths are relative and must resolve inside the case directory. No code is
executed from manifests. Inspect a received case's text before running it, and preserve
the source manifest with your result. The report records input hashes and full configuration.

## Field-study acceptance

Follow [FIELD_PROTOCOL.md](FIELD_PROTOCOL.md). A match that changes greatly under
plausible clock, temperature, source-tone or height changes remains inconclusive.
The experimental CLI never labels an output an accepted location.
